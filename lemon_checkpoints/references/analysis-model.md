# 分析模型

## 输入底稿

先记录三类信息：

| 类型 | 含义 | 示例 |
|---|---|---|
| 已确认 | 需求原文、截图或接口文档直接证明 | 页面存在验证码输入框 |
| 验证建议 | 行业测试方法要求关注，但材料没有给出规则 | 检查验证码是否可重复使用 |
| 待确认 | 不同答案会改变预期结果或优先级 | 验证码有效期是多少 |

建议不能伪装成需求。测试点引用建议时，预期结果写清需要按哪项规则确认。

## 风险路线

不要先按技术维度拆表。先按用户完成目标的顺序建立路线，例如：

```text
进入页面 → 提供信息 → 系统校验 → 结果反馈 → 保持或结束会话
```

每一段检查：

- 用户是否能继续完成目标。
- 错误是否被发现并给出反馈。
- 敏感数据是否可能泄露。
- 多次或同时操作是否产生不一致。
- 中断后是否可以安全恢复。

## 执行批次

| 批次 | 选择标准 | 典型用途 |
|---|---|---|
| A 首轮冒烟 | 最短成功路径、关键页面、必要输入、阻断性安全控制 | 每次构建先执行 |
| B 重点验证 | 主要失败、边界、权限、状态、重复、并发和恢复 | 功能测试主体 |
| C 扩展检查 | 兼容、性能、日志、低频组合和历史影响 | 上线前或专项执行 |

同一场景只放入一个批次。另一个批次需要引用时，写关联编号，不复制整条内容。

## 测试清单字段

| 字段 | 作用 |
|---|---|
| 检查编号 | 使用 `LC-001` 连续编号 |
| 执行批次 | A、B或C |
| 业务链路 | 用户目标中的具体阶段 |
| 风险主题 | 功能、数据、安全、恢复、性能或兼容 |
| 触发情况 | 一句话写清发生什么 |
| 样本数据 | 具体账号、值、状态、时间或组合 |
| 核对结果 | 可以从页面、接口、数据、消息或日志确认的结果 |
| 证据级别 | 已确认、验证建议或待确认 |
| 关联项 | 规则 `F-XXX` 或问题 `O-XXX` |
| 严重度 | S0至S3 |
| 执行方式 | 人工、自动化或组合，并写原因 |
| 失败影响 | 对业务或用户造成的直接后果 |
